# Мотивация для менеджмента

### Преимущества

- **Повышение надёжности системы и более быстрое обнаружение проблем**.
  С помощью мониторинга команда сможет быстрее определить факт наличия проблем в системе и приблизительное место (сервис) её возникновения. Следовательно её будет проще устранить, т.к. команда не будет тратить время на поиски и проверку гипотез. В отсутствие такой обратной связи, проблема может быть пропущена или обнаружена слишком поздно, что займет больше времени и обойдется компании дороже. Обычно, тем раньше и точнее диагностирована проблема, тем быстрее и дешевле обходится её решение, хотя бы временное.

    > Можно привести пример с автомобилем. Если будет отсутствовать датчик давления масла, то в случае отказа насоса, двигатель ещё некоторое время будет работать. Но через несколько минут произойдет заклинивание и двигатель выйдет из строя. В этом случае ремонт станет невозможным или чрезвычайно дорогим.

- **Повышение безопасности системы**:
  Мониторинг существенно повысит безопасность системы. Популярные сервисы становятся интересны злоумышленникам, которые могут действовать для личной выгоды или по наводке недобросовестных конкурентов. Правильно настроенные оповещения об инцидентах позволят специалисту по безопасности или DevOps немедленно принять меры противодействия. Это позволит предотвратить или уменьшить ущерб от кражи персональных данных или повреждения инфраструктуры, а значит, уменьшить риски нарушения законодательства и финансовые потери.

- **Повышение быстродействия системы и эффективное распределение ресурсов**:
    - С помощью мониторинга DevOps смогут выявлять узкие места. Мониторинг позволит им определить места и сценарии нагрузки, при которых те или иные сервисы не справляются с работой или приводят к большому числу ошибок. Это позволит команде разработки и DevOps выбирать наилучшее решение по оптимизации системы обоснованно, опираясь на числовые показатели, а не абстрактные идеи.
    - Метрики позволят правильно настроить автоматическое масштабирование. Конкретное количество выделяемых ресурсов будет подстраиваться под нагрузку, что позволит сэкономить средства, особенно в условиях облачной инфраструктуры.

- **Ускорение рабочего процесса и DevOps**:
  В настоящее время развёртывание в `release` и `production` требуют ручного труда. Мониторинг позволит снизить нагрузку на DevOps команду. Часть проблем может быть обнаружена автоматически, что приведёт к оповещению ответственных специалистов.

- **Ценные бизнес-инсайты**:
  Накопление статистики поведения пользователей позволит менеджеру продукта более точно определять потребности клиентов и корректно определять тренды, а маркетологам формировать точечные и персональные рекламные компании.

- **Общее повышение удовлетворённости пользователей**:
  Обобщая всё вышесказанное, можно сделать вывод, что оперативное решение проблем, повышение производительности и стабильности работы системы приведут к положительным отзывам клиентов. Это, в свою очередь, позволит увеличить число клиентов через "сарафанное радио" и сервисы отзывов.

### Недостатки

- **Потребуется развертывание дополнительной инфраструктуры** (аренда у облачного провайдера). В целом потребление ресурсов может вырасти на 5-20%, в зависимости от нагрузки.

- **Возрастёт нагрузка на текущую инфраструктуру**. Например, на сеть. Если она тарифицируется отдельно, повысятся расходы и в этой части.

- **Потребуется найм дополнительных специалистов**:
    - Как минимум одного Dev**Ops**, который будет следить за состоянием системы и осуществлять настройку инструментов мониторинга.
    - А также, минимум одного специалиста по безопасности, который будет контролировать аспекты доступа и общую безопасность системы.

- **Развёртывание и адаптация займет время и будет иметь побочные эффекты**:
    - Потребуется подстройка инструментов мониторинга под приложение. Возможно небольшое общее замедление работы приложения.
    - Потребуется обучение текущих специалистов, например, DevOps (по настройке инструментов мониторинга) и программистов (для реализации кастомных метрик). В этот период они будут частично оторваны от текущей работы (реализации новых функций и доработки системы).

**Мониторинг не является бесплатной функцией. Однако его внедрение окупится за счёт средств, которые компания перестанет терять из-за постоянных проблем с заказами и производительностью.**

Данные эффекты не возникнут единовременно. Процесс интеграции инструментов мониторинга будет производиться постепенно и в первую очередь для самых нагруженных и проблемных сервисов, а потому расходы будут расти постепенно, компенсируясь новыми заказами.

# Выбор подхода к мониторингу

Для систем, взаимодействующих с пользователями (API) необходимо использовать RED подход. Он позволит определять характер взаимодействия пользователей с приложением, выполнять автоматическое масштабирование и контролировать безопасность.

Список сервисов с RED подходом:

- Shop API
- CRM API
- MES API

Для всех систем в принципе, включая указанные выше, следует использовать USE подход, чтобы контролировать использование ресурсов (CPU, памяти, дисков и т.п.):

- Для баз данных и в особенности для 3D хранилища необходимо контролировать, в первую очередь, расход дискового пространства, чтобы не выйти за лимиты.
- Т.к. тарификация у облачных провайдеров обычно происходит за использованные ресурсы, наличие мониторинга позволит компании эффективно планировать расход средств на инфраструктуру на месяцы вперёд и учитывать различные профили нагрузки, например, периоды перед крупными праздниками.
- Контроль CPU и памяти - это самый простой способ организации масштабирования.

В таблице, значение Nмакс.стат подразумевает максимально допустимое значение, определённое на основе статистики работы сервиса и нагрузочных тестов. Название одно для простоты, но подразумевает статистику соответствующего показателя. Зависит от мощности серверов, настроек лимитов Web-серверов и времени обработки одного запроса.

Для выполнения оперативного контроля числа запросов и выполнения отказов (429 Too Many Requests) потребуется настройка Web-сервера или внедрение API Gateway с расширениями.

# План действий

1. Добавить API Gateway и настроить его на сбор статистики и выдачу метрик по запросам
2. Настроить Rate Limiter в API Gateway для возврата 429 Too Many Requests.
3. Добавить дополнительные сервисы, для преобразования стандартных метрик Yandex Cloud в формат, доступный Prometheus
4. Убедиться, что в RabbitMQ включена и настроена DLQ
5. Поднять Prometheus
6. Настроить в Prometheus сбор логов из API Gateway, сервисов и Yandex Managed PostgreSQL.
7. Определить статические лимиты на основе текущей конфигурации
8. Настроить в Prometheus оповещения и действия, при превышении лимитов
9. Собирать статистику времени выполнения и количества запросов
10. Провести нагрузочное тестирование для определения порогов (thresholds)
11. Настроить в Prometheus оповещения и действия, при превышении порогов
